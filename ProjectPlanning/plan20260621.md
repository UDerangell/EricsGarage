## Phase 2 — MIDI Domain Model (Week 2–3)

### 2.1 Core Data Structures

Design immutable, extensible event records using Clojure maps with a required `:type` dispatch key. All events share a common envelope; type-specific keys are additive:

```clojure
;; Common envelope — every MIDI event
{:type        :note-on          ;; dispatch key — extensible via keyword
 :source      :port             ;; :port | :file
 :source-id   "USB MIDI Interface"
 :channel     1                 ;; 1–16
 :timestamp   1234567890        ;; System/nanoTime
 :raw         [0x90 0x3C 0x7F] ;; original bytes preserved

 ;; Note-specific keys
 :note        60                ;; MIDI note number 0–127
 :velocity    127}              ;; 0–127

;; Controller event — same envelope, different keys
{:type        :control-change
 :channel     1
 :timestamp   ...
 :controller  74                ;; filter cutoff, mod wheel, etc.
 :value       64}

;; Future extensibility examples (no code changes needed to bus/state)
{:type :pitch-bend   :channel 1 :value 8192}
{:type :program-change :channel 1 :program 42}
{:type :sysex        :data [0xF0 0x41 ...]}
{:type :meta         :meta-type :tempo :bpm 120.0}
```

### 2.2 Event Specs
- `clojure.spec` definitions for each event type
- Instrumented during development; stripped for production builds
- Spec registry allows third-party event types without touching core

## Phase 3 — MIDI Source Layer (Week 3–4)

### 3.1 Hardware Port Listener
- Enumerate `MidiSystem/getMidiDeviceInfo` at startup; match against configured names
- Open receivers on each matched input device
- Implement `javax.sound.midi.Receiver` in Java or via `proxy` in Clojure
- Convert `MidiMessage` objects → normalized event maps
- Put events onto core.async channel (non-blocking; drop or buffer on overflow)

### 3.2 MIDI File Reader
- Use `MidiSystem/getSequencer` to load `.mid` files
- Implement a custom `Receiver` attached to the sequencer's transmitter
- Emit events with `:source :file` and `:source-id` of the filename
- Support simultaneous playback of multiple files
- Expose transport controls (play, pause, stop, seek) via `core.async` command channel

### 3.3 Source Multiplexer
- Both sources put onto a single shared `core.async` channel
- Back-pressure strategy defined here (sliding buffer recommended for live use)

## Phase 4 — Event Bus & Application State (Week 4–5)

### 4.1 Event Bus (`midi-vis.events.bus`)
- Single `core.async` channel as the event spine
- `go-loop` consumers for:
  - State updater (primary consumer)
  - Logger / recorder (tap)
  - Future: OSC output, network relay
- `mult` + `tap` pattern so multiple consumers can subscribe without competing

### 4.2 Application State (`midi-vis.state`)

Central `atom` holding the entire render-relevant world:

```clojure
{:active-notes
 {1  {60 {:velocity 100 :on-at 123456789}
      64 {:velocity 80  :on-at 123456790}}
  10 {38 {:velocity 110 :on-at 123456791}}}

 :channel-states
 {1  {:program 0  :pitch-bend 8192 :controllers {}}
  ...}

 :history
 []   ;; ring buffer of recent events for scrolling display

 :transport
 {:playing? true :position-ms 4200 :source :file}}
```

- State transitions are pure functions: `(fn [state event] new-state)`
- The `go-loop` calls `swap!` with the appropriate transition function dispatched on `:type`
- Watchers on the atom trigger GUI repaints (rate-limited to configured FPS)

## Phase 5 — GUI Layer (Week 5–7)

### 5.1 Framework Selection
- **Recommended: cljfx** (JavaFX wrapper) — declarative, React-like, excellent for data-driven rendering
- Fallback: Seesaw (Swing) if JavaFX deployment is a concern

### 5.2 Channel Column View (Initial Scope)

**Layout:** 16 equal-width columns, full window height

**Per-column rendering logic:**
```
Column height maps to note range 0–127 (bottom = 0, top = 127)
Rectangle y-position  = (1 - note/127) × column-height
Rectangle height      = fixed minimum (e.g. 8px) for visibility
Rectangle width       = (velocity/127) × column-width
Rectangle x-offset    = (column-width - rect-width) / 2  ;; centered
Color                 = channel color from config, alpha = velocity/127
```

- Active notes (Note On received, Note Off not yet received) rendered as solid rectangles
- Note Off transitions rectangle to fade-out animation (opacity decay over ~200ms)
- Channel 10 (drums) optionally rendered with a different shape or color scheme

### 5.3 Rendering Pipeline
- State atom watcher fires at most once per frame (16ms @ 60fps)
- Pure function: `(fn [app-state] scene-description)` — no side effects
- cljfx reconciles scene description diff → minimal JavaFX updates
- All GUI mutations on JavaFX Application Thread via `Platform/runLater`

### 5.4 Extensibility Points in GUI
- `defmulti render-channel-event` dispatched on `:type` — adding controller rendering requires only a new method
- Per-channel plugin slots in the column (reserved space above/below note area for future controller lanes)
- Scene description is a plain Clojure map — serializable, testable, diffable

## Phase 6 — Integration & Wiring (Week 7–8)

### 6.1 System Startup Sequence
```
1. Load & validate config.edn
2. Initialize app-state atom
3. Create core.async event bus (mult + taps)
4. Open MIDI port listeners (per config)
5. Open MIDI file sequencer(s) (per config)
6. Start state-updater go-loop
7. Launch GUI (on JavaFX thread)
8. Register state atom watcher → GUI repaint
9. Begin MIDI file playback (if configured)
```

### 6.2 System Shutdown
- Close all MIDI receivers and transmitters
- Stop all `go-loop`s via poison pill or `close!` on channels
- Flush any pending state writes
- Dispose JavaFX stage

### 6.3 Error Handling Strategy
- MIDI device not found → log warning, continue with available devices
- Malformed MIDI message → log and discard; never crash the bus
- Config validation failure → print human-readable spec explain, exit with code 1
- GUI exception → isolated; does not affect event pipeline

# REFINEMENT PROMPT:

If input will exclusively be from a MIDI file it is possible to optimize the display based on the MIDI data in the file.  Only channels that contain note data need to be rendered.  The vertical note range can be restricted to the minimum and maximum note numbers found in the data.  How would this optimization requirement impact the project plan, where optimization would automatically be done when a new MIDI file is loaded.

## Impact Analysis: MIDI File Pre-Analysis Optimization

This is a well-contained addition that touches three existing layers and introduces one new sub-layer. Here's how it propagates through the plan.

---

## New Sub-Layer: MIDI File Analyzer

Insert between the **MIDI Source Layer** and the **Event Bus Layer**:

```
┌─────────────────────────────────────────────┐
│              GUI Layer                      │
├─────────────────────────────────────────────┤
│           Presentation Layer                │
├─────────────────────────────────────────────┤
│           Event Bus Layer                   │
├─────────────────────────────────────────────┤
│         MIDI Domain Layer                   │
├─────────────────────────────────────────────┤
│   *** MIDI File Analyzer (NEW) ***          │  ← inserted here
├─────────────────────────────────────────────┤
│           MIDI Source Layer                 │
├─────────────────────────────────────────────┤
│           Config Layer                      │
└─────────────────────────────────────────────┘
```

Namespace: `midi-vis.midi.analysis`

This layer is a **pure, read-only pass** over the MIDI file's sequence data before playback begins. It never touches the event bus or mutates application state directly — it produces a value that is loaded into the state atom during file initialization.

---

## New Data Structure: File Analysis Result

```clojure
{:source-id   "/path/to/song.mid"
 :analyzed-at 1234567890

 :active-channels #{1 3 5 9 10}   ;; channels with at least one note event

 :channel-ranges
 {1  {:min-note 48  :max-note 84}  ;; per-channel note extent
  3  {:min-note 52  :max-note 76}
  5  {:min-note 40  :max-note 64}
  9  {:min-note 35  :max-note 35}  ;; kick only
  10 {:min-note 35  :max-note 59}} ;; full drum kit

 :global-range
 {:min-note 35  :max-note 84}      ;; union across all active channels

 :duration-ms  214000
 :tempo-map    [{:tick 0    :bpm 120.0}
                {:tick 3840 :bpm 110.0}]
 :time-signatures [{:tick 0 :numerator 4 :denominator 4}]}
```

The `tempo-map` and `time-signatures` are included at no extra cost during the same scan pass — they will be needed eventually and cost nothing to collect now.

## Impact by Layer

### Config Layer — Minor Addition

Add an `analysis` section to `config.edn` to give users control over the optimization behavior:

```clojure
:analysis
{:auto-analyze?        true   ;; run analysis on every file load
 :channel-filter       :auto  ;; :auto | :all | #{1 3 5} explicit set
 :note-range           :auto  ;; :auto | :all | {:min 36 :max 96} explicit
 :note-range-padding   2}     ;; semitones of margin above/below detected range
```

The padding option is important: a `:auto` range with zero padding causes the highest and lowest notes to render at the very edge of the column with no visual breathing room.

---

### MIDI Source Layer — Sequencing Change

The file reader startup sequence changes from:

```
open file → start playback → emit events
```

to:

```
open file → run analyzer → load analysis into state → start playback → emit events
```

The analyzer reads the `Sequence` object directly from `MidiSystem/getSequence` — the same object the sequencer will play back — so there is no redundant I/O. The file is read from disk once.

```clojure
(defn prepare-file-source [path config]
  (let [sequence  (MidiSystem/getSequence (io/file path))
        analysis  (analyzer/analyze-sequence sequence path)
        sequencer (MidiSystem/getSequencer)]
    (.setSequence sequencer sequence)
    {:sequencer sequencer
     :analysis  analysis}))
```

The analysis result is returned alongside the sequencer handle and passed to the state initializer before playback begins.

---

### Application State — Additive Change

Extend the state atom to carry the active analysis:

```clojure
{:active-notes    { ... }
 :channel-states  { ... }
 :history         []
 :transport       { ... }

 ;; NEW
 :file-analysis
 {:source-id      "/path/to/song.mid"
  :active-channels #{1 3 5 9 10}
  :channel-ranges  { ... }
  :global-range    {:min-note 35 :max-note 84}
  :duration-ms     214000
  :tempo-map       [ ... ]}}
```

When input source is ports only, `:file-analysis` is `nil` and the GUI falls back to rendering all 16 channels across the full 0–127 range — no special casing needed anywhere else.

When a new file is loaded mid-session the state transition is:

```clojure
(swap! app-state assoc :file-analysis new-analysis
                       :active-notes  {}
                       :transport     initial-transport)
```

One atomic swap clears stale note state and installs the new analysis simultaneously, preventing any frame from rendering a mix of old and new data.

### GUI Layer — Driven by State, No Structural Change

The rendering pipeline already reads from the state atom. The column renderer becomes a function of the analysis:

**Column visibility:**
```clojure
(defn visible-channels [state]
  (if-let [analysis (:file-analysis state)]
    (:active-channels analysis)
    (set (range 1 17))))   ;; all 16 when no file analysis available
```

**Note-to-Y mapping becomes per-channel (or global):**
```clojure
(defn note->y [note channel column-height state]
  (let [analysis (:file-analysis state)
        {:keys [min-note max-note]}
          (or (get-in analysis [:channel-ranges channel])
              (:global-range analysis)
              {:min-note 0 :max-note 127})
        padding  (get-in state [:config :analysis :note-range-padding] 2)
        lo       (max 0   (- min-note padding))
        hi       (min 127 (+ max-note padding))
        span     (- hi lo)]
    (* column-height (/ (- hi note) span))))
```

The columns widen automatically when fewer than 16 are active — the layout simply divides window width by `(count visible-channels)` instead of a fixed 16.

### New Phase: Analyzer Implementation

Insert as **Phase 3b** between the current Phase 3 (MIDI Source Layer) and Phase 4 (Event Bus):

**Phase 3b — MIDI File Analyzer (add ~1 week)**

- Iterate over all `Track` objects in the `Sequence` without starting the sequencer
- Walk each `MidiEvent` in each track, inspecting `MidiMessage` type
- Collect per-channel note min/max, active channel set, tempo/time signature meta events
- Return the analysis map; no side effects
- Wire into `prepare-file-source` so analysis is always complete before the state atom is updated
- Handle edge cases:
  - Files where Note On with velocity 0 is used as Note Off (common) — count these correctly
  - Channels with only controller or program change data but no notes — excluded from `:active-channels`
  - Empty tracks (common in multi-track files) — skipped cleanly
  - Files with no notes at all — return a safe default analysis with a warning
